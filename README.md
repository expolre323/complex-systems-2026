作业 01 页面沿课堂给的六个层级完整拆开，并对每一层给出可检验的内容：

| 层级 | 本页给出的东西 | 数量 |
|---|---|---|
| 01 任务 Mission | 主任务 + 4 项支援任务、任务四要素、MOE/MOS/MOP 三层度量、三种任务语境下的六层差异 | 1 + 4 + 10 条度量 |
| 02 体系 SoS | 五条体系判据、7 类成员系统（给什么/取什么）、5 类接口量化约束、涌现能力、边界声明 | 7 成员 / 5 接口 |
| 03 整机 Vehicle | 构型空间穷举、5 个候选方案、可拖拽权重 + 四组预设的决策矩阵、4 种机动模态、12 项基线指标 | 5 方案 |
| 04 系统 Systems | 11 个一级系统，按四类归口，每个都有职责/指标/接口/失效影响 | 11 |
| 05 子系统 Sub-systems | 按系统分组，功能完整、可整体更换 | 47 |

| 07 追溯 Traceability | 6 条抽样链，逐层回答"为什么上一层需要它"；点击任意模块可反查 | 6 链 + 188 可查 |
| 08 预算 Budget | 质量 1400 kg / 功率 48 kW 峰值 / 信息流 5.8 Gbps 三项闭合，并给出三项**余量**（100 kg / 12 kW / 4.2 Gbps）与自评 | 3 张预算表 |

体系层另有一张**四类体系定位表**（Maier 1998 的 directed / acknowledged / collaborative / virtual），把 IBEX-01 判定为「公认体系」，并由此推出三条对下游的约束：不能假设成员能力、目标不归工程师定义、平台是能力提供者而非决策者。末尾的 **HANDOVER** 区列出交给作业 02 的三样锚点（S01–S11 编号、五类体系接口、MOE/MOS/MOP）。

### 作业 02 页面（`a2.html`）

依据郭宝柱《系统工程——基于国际标准过程的研究与实践》第 4 章，**严格按表 4-1（BRS）与表 4-5（StRS）的章节轮廓输出**两份规格说明，并展开作业要求的五个重点论述：

| 区块 | 内容 | 数量 |
|---|---|---|
| 02 两份文档 | BRS 20 节 / StRS 23 节的正文阅读器，左侧章节目录可直接切换 | 2 份 / 43 节 |
| 03 业务与任务需求 | 4 个量化痛点、6 条业务需求 BRQ、10 条任务需求 TR（挂到作业 01 的 MOE/MOS/MOP）、SMART 检验 | 6 + 10 |
| 04 运营概念 ConOps | 组织层多对多：三阶段 × 五角色运行节拍表、角色职责、5 条运行假设、4 条 What-if | 3 阶段 |
| 05 运行概念 OpsCon | 系统层一对多：11 个状态（7 正常 + 4 降级）状态机、5 个运行场景、6 条 What-if | 11 状态 / 5 场景 |
| 06 相关方列表 | 18 类相关方（三分法）、影响力—利益四象限、表 4-3 分析矩阵、四种管理策略，外加 **权力·合法性·紧迫性显著性模型**（Mitchell 1997）与两个模型的交叉校验 | 18 类 / 6 型 |
| 07 相关方需求 | 40 条 StR（10 个类别，按优先级/关键词筛选）、**ISO/IEC/IEEE 29148 九项判据**逐条对照与一组「初稿 → 改后」实检、3 组「需要→需求」转换、5 处冲突与协商 | 40 条 / 9 判据 |
| 08 追溯 | 业务需求 → 任务度量 → 相关方需求 → S01–S11 的四线追溯矩阵 | 10 行 |
| 09 验证与确认 | 验证 vs 确认对照、四种验证方法（T/A/D/T 判据）、基线冻结后的变更控制（申请 → 影响分析 → CCB）与一次完整走例 | 2 表 + 3 步 |

作业 02 在两处显式回指作业 01：04/05 节开头用一张表把 **ConOps 与 OpsCon 的边界**钉死（主语是「各方」还是「这一台」）；06 节的显著性模型解释了为什么平民与公众在影响力—利益矩阵里垫底，却仍能触发一条「必须」级需求。

## 四、改内容时改哪里

**文字与数据都在 `assets/js/` 的两个文件里，页面结构不用动。**

| 想改的东西 | 改这里 |
|---|---|
| 质量 / 功率 / 信息流预算的分配值 | `data.js → budget`（`rows[].kg` / `.kw` / `.rate`），页面上的柱条与合计会自动重算 |
| 11 个系统的职责、指标、接口 | `data.js → systems` |
| 40 条需求的内容、优先级、验证方法、来源 | `a2-data.js → reqs.items` |
| 相关方的坐标（决定四象限里的位置） | `a2-data.js → stake.groups[].items[].pw / .it` |
| 业务需求、任务需求、场景、状态 | `a2-data.js → biz` / `opscon` |
| 首页两张卡的标题、要点、日期 | `data.js → roadmap`（`q` 是那张卡上的「核心问题」，`keys` 是三条要点） |

改完刷新即可，没有任何构建步骤。

### 如果老师又加了第三次作业

1. 复制 `a2.html` 为 `a3.html`，替换章节内容，样式与脚本路径不变；
2. 新建 `assets/js/a3-data.js`，末尾写 `window.CSE.a3 = { /* 数据 */ }`，页面按 `data.js → a3-data.js → fx.js → a3.js` 的顺序引入；
3. 在 `data.js → roadmap` 数组里追加一条 `{ no: '03', name: …, href: 'a3.html', status: 'published', q: …, keys: [...] }`，首页会自动长出第三张卡。

> 首页只做索引，不做内容堆叠：**一次作业一个 URL**。这样单次成果可以直接发给老师，也不会因为后续补充把前面的结论改得对不上。

### 日常更新（改了内容之后）

```bash
git add -A
git commit -m "作业 03：系统架构"
git push
```

推送后 GitHub 会自动重新构建，约 30–60 秒生效（Actions 里能看到 `pages build and deployment`）。

### 另建一个仓库时

```bash
git remote set-url origin https://github.com/<用户名>/<新仓库名>.git
git push -u origin main
```

然后仓库 **Settings → Pages**：Source 选 `Deploy from a branch`，分支 `main`，目录 `/ (root)`，保存。

> 若仓库名就叫 `<用户名>.github.io`，则站点直接在 `https://<用户名>.github.io/` 根路径。

### 换自定义域名

在仓库 **Settings → Pages → Custom domain** 填域名，并把 DNS 的 `CNAME` 记录指向 `<用户名>.github.io`；勾选 `Enforce HTTPS`。仓库根目录会自动生成 `CNAME` 文件，不要删。

## 七、内容口径

- 所有质量、功率、速率、指标均为**课程概念设计目标**，用于演示"分解—分配—闭合"的方法，不代表任何在研或在役装备的真实参数。
- 作业 02 的两份文档按 **ISO/IEC/IEEE 29148:2018** 的 BRS / StRS 范例轮廓（郭宝柱书表 4-1、表 4-5）组织章节；相关方清单按该章"直接相关方 / 生命周期交互与使能系统 / 施加影响与被影响"三分法抽象为 18 类，矩阵按表 4-3 的列项填写。
- 需求条目全部使用"应（shall）"句式，每条只表达一个需求，标注优先级（必须 / 应该 / 可能）与主验证方法（T 试验 / A 分析 / D 演示 / I 检查），并给出相关方来源与追溯目标。
- 平台代号 **IBEX-01** 为小组概念编号，无其他命名含义。
- 涉及效应的部分明确写为"目标指示与效应交接"，杀伤决策始终由授权人员作出，与课堂强调的安全边界一致。
